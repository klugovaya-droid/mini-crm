# Мини-CRM «Объекты и задачи»

Небольшая CRM для строительной компании. Руководитель создаёт объекты и задачи, назначает исполнителей, принимает работу или возвращает её на доработку. Исполнитель видит только свои задачи и объекты, где у него есть задачи.

Главный акцент — безопасность на уровне PostgreSQL/Supabase: ограничения работают даже при прямом запросе к API, а не только в интерфейсе.

## Стек

- React 19 + TypeScript + Vite
- Tailwind CSS v4 + shadcn/ui
- React Router, TanStack Query
- Supabase: PostgreSQL, PostgREST, Auth
- Vitest + Testing Library
- Playwright как драйвер e2e (Vitest — раннер)

## Быстрый старт

Требования: Node.js 20+, Docker Desktop, Supabase CLI (устанавливается как dev-зависимость).

```bash
npm install
npm run db:start       # локальный Supabase
npm run env:local      # записать локальные ключи в .env.local
npm run seed:local     # пользователи, объекты, задачи и история
npm run dev
```

Приложение откроется на `http://localhost:5173`.

### Тестовые аккаунты (локально)

| Роль | Email | Пароль |
| --- | --- | --- |
| Руководитель | `manager@demo.local` | `Demo1234!` |
| Исполнитель | `worker1@demo.local` | `Demo1234!` |
| Исполнитель | `worker2@demo.local` | `Demo1234!` |

Пароль задаётся переменной `DEMO_PASSWORD` при seed. Эти аккаунты предназначены только для локальной разработки и демо.

### Если локальный Supabase не стартует

Локальный стек запускается без необязательных сервисов (Studio, Realtime, Storage), чтобы работать на слабых машинах. Если Docker всё равно не тянет образы, проверьте, что запущен Docker Desktop и доступен `public.ecr.aws`. В крайнем случае можно использовать отдельный облачный Supabase-проект только для разработки.

## Роли и сценарии

### Руководитель

- видит все объекты, задачи и историю;
- создаёт, редактирует и архивирует объекты;
- создаёт, редактирует и архивирует задачи;
- назначает исполнителя;
- принимает задачу или возвращает на доработку с обязательным комментарием.

### Исполнитель

- видит только задачи, назначенные на него, и объекты, где у него есть задачи;
- берёт задачу в работу;
- отправляет на проверку;
- продолжает работу после возврата на доработку;
- видит историю своих задач.

Все ограничения продублированы в базе. Если исполнитель попробует прочитать чужую задачу или вызвать запрещённый переход через API, Supabase вернёт пустой результат или ошибку.

## Статусы

```text
Новая → В работе → На проверке → Принята
                         ↓
                    На доработке → В работе
```

| Из | В | Кто |
| --- | --- | --- |
| — | Новая | руководитель (создание) |
| Новая | В работе | назначенный исполнитель |
| В работе | На проверке | назначенный исполнитель |
| На проверке | Принята | руководитель |
| На проверке | На доработке | руководитель, комментарий обязателен |
| На доработке | В работе | назначенный исполнитель |

Другие переходы запрещены.

## Безопасность

### RLS

RLS включён на всех таблицах, политики по умолчанию запрещают доступ.

| Таблица | Что видит руководитель | Что видит исполнитель |
| --- | --- | --- |
| `profiles` | всех | себя, руководителей и авторов своих задач |
| `projects` | все | только объекты с активной задачей на него |
| `tasks` | все | только задачи, где он исполнитель, и только по активному объекту |
| `task_status_history` | всю историю | историю только своих задач |

Прямые `INSERT`/`UPDATE`/`DELETE` объектов и задач исполнителю не выданы. Удаление — мягкое (`deleted_at`), поэтому история не стирается вместе с задачей.

### Переходы статусов

Статус меняется только через `public.transition_task(...)`:

- функция блокирует строку задачи;
- проверяет роль, исполнителя и пару «откуда → куда»;
- требует комментарий для возврата на доработку;
- обновляет задачу и пишет историю в одной транзакции.

Прямой `UPDATE tasks SET status = ...` запрещён на уровне GRANT и защитного триггера. Это значит, что запрещённый переход не пройдёт даже при ручном запросе с токеном пользователя.

### История

`task_status_history` — append-only:

- у клиентских ролей нет прав на `INSERT`, `UPDATE`, `DELETE`;
- `INSERT` отозван даже у `service_role`;
- `UPDATE`/`DELETE` дополнительно блокируются триггером;
- создание задачи пишется как `null → Новая`;
- каждая смена статуса сохраняет автора, время, старый статус, новый статус и комментарий.

### Ключи и регистрация

- во фронтенд попадает только `anon key`;
- `service_role` используется только локальными скриптами seed/verify и не коммитится;
- `.env*` в `.gitignore`;
- `npm run check:secrets` проверяет, что в клиентском коде нет ссылок на service-role;
- открытая регистрация выключена в `supabase/config.toml`; в облаке её нужно выключить в Dashboard.

### Что не может сделать исполнитель

- прочитать или изменить чужую задачу;
- увидеть объект, где у него нет задач;
- создать, отредактировать или архивировать объект/задачу;
- назначить исполнителя;
- принять задачу или вернуть её на доработку;
- перейти в статус, не предусмотренный матрицей;
- изменить или удалить историю;
- повысить себе роль.

## Деплой

### Supabase (облако)

1. Создайте проект в Supabase.
2. Выполните `npx supabase login`, затем `npx supabase link --project-ref <ref>`.
3. Примените миграции: `npx supabase db push`.
4. Выключите Email signups и anonymous sign-ins в Authentication → Providers.
5. Укажите Site URL и redirect URL вашего приложения.
6. Создайте `.env.production.local`:

```dotenv
SUPABASE_URL=https://<project>.supabase.co
SUPABASE_ANON_KEY=<anon key>
SUPABASE_SERVICE_ROLE_KEY=<service role key>
DEMO_PASSWORD=<пароль для демо-аккаунтов>
```

7. Запустите seed локально: `npm run seed:cloud`.

Скрипт создаёт пользователей через Admin API, поэтому `service_role` остаётся на машине разработчика и не попадает в приложение.

### Vercel

1. Импортируйте репозиторий в Vercel.
2. Build command: `npm run build`; output: `dist`.
3. Добавьте переменные окружения:
   - `VITE_SUPABASE_URL`
   - `VITE_SUPABASE_ANON_KEY`
4. Задеплойте. `vercel.json` уже содержит rewrite для SPA-маршрутов.

После деплоя проверьте защиту:

```bash
npm run verify:prod
```

Скрипт проверяет, что регистрация закрыта, исполнитель не читает чужие данные, прямой смене статуса и изменению истории приходит отказ.

## Тесты

- **Unit** — матрица переходов, права, валидация форм, ошибки, подписи статусов.
- **Integration** — реальные JWT и PostgREST: RLS, запреты, переходы, история, service-role-атаки.
- **E2E** — вход, объекты, задачи, полный workflow, архивация, мобильная навигация.

Перед сдачей:

```bash
npm run validate
npm run build
```

## Решения и допущения

Подробно — в [`docs/decisions.md`](docs/decisions.md). Кратко:

- одна роль на пользователя;
- мягкое удаление объектов и задач;
- история ведётся только по статусам;
- комментарий обязателен только при возврате на доработку;
- руководитель может редактировать поля активной задачи, но не статус в обход workflow;
- открытая регистрация выключена; пользователи создаются через seed/Admin API.
