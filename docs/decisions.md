# Решения и допущения

## Что решено самостоятельно

1. **Одна роль на пользователя.** Роль хранится в `public.profiles.role` (`manager` или `worker`). Пользователи с несколькими ролями в ТЗ не описаны, поэтому смешивать роли не стал.
2. **Мягкое удаление.** У объектов и задач есть `deleted_at`. Кнопка «Архивировать» скрывает запись из обычных списков, но оставляет задачи и историю в базе. Это защищает аудит: историю нельзя стереть, удалив задачу.
3. **Архивирование объекта.** Объект скрывается вместе со своими задачами. Задачи и история физически остаются; исполнитель перестаёт их видеть.
4. **История только по статусам.** Название, описание, исполнитель и объект в историю не попадают — ТЗ требует историю смены статусов. Это сознательное ограничение, а не недоделка.
5. **Комментарий.** Обязателен только при переходе «На проверке → На доработке». Для остальных переходов поле необязательное; если комментарий заполнен, он сохраняется.
6. **Редактирование задачи руководителем.** Руководитель может менять поля активной задачи в любом статусе, но не может менять статус в обход кнопок workflow. Принятую задачу можно архивировать.
7. **Видимость профилей.** Исполнитель видит себя, руководителей и авторов своих задач; руководитель видит всех. Полный справочник сотрудников исполнителю не нужен.
8. **Новые пользователи.** Триггер на `auth.users` создаёт профиль с ролью `worker` по умолчанию. Назначение роли `manager` выполняется через seed/Admin API или SQL, потому что `app_metadata` устанавливается после срабатывания insert-триггера. Это безопаснее, чем доверять пользовательским метаданным.
9. **Локальный Supabase.** Для экономии памяти отключены Studio, Realtime, Storage, Edge Runtime и аналитика. Для задания они не нужны.
10. **Тестовые данные.** 1 руководитель, 2 исполнителя, 3 объекта, 6 задач во всех статусах, включая задачу с комментарием на доработке.
11. **Ошибки.** База возвращает коды `MC###`, фронтенд переводит их в понятные русские сообщения. Сырые тексты ошибок не показываются пользователю.
12. **Проверка защиты.** Integration-тесты ходят в PostgREST с реальными JWT пользователей, а не через SQL-суперпользователя. Так проверяется именно тот путь, которым может пойти злоумышленник.

## Что не успел / сознательно не делал

- Realtime-обновления и уведомления.
- Загрузку файлов и фотоотчётов к задачам.
- Отдельный экран управления пользователями и ролями.
- Восстановление пароля через собственный экран (стандартный Supabase flow можно включить отдельно).
- Пагинацию, поиск и сложные фильтры.
- Аудит изменения нестатусных полей задачи.
- Мобильное приложение, i18n, тёмную тему.
- Rate limiting и мониторинг production-уровня.
- CI-пайплайн: проверки запускаются локально командой `npm run validate`. GitHub Actions можно добавить отдельным шагом, но он потребует Docker и Supabase CLI в runner.

## Известные ограничения

- Free tier Supabase может «засыпать» после периода неактивности; первый запрос после паузы будет медленнее.
- Если объект архивирован, его задачи нельзя продолжить по workflow — это ожидаемо.
- История не удаляется даже при очистке демо-данных; для локальной разработки используется `npm run db:reset`.
- В облаке открытую регистрацию нужно выключить вручную в Supabase Dashboard: `config.toml` управляет только локальным стеком.
